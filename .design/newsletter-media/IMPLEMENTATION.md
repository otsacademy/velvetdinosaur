# Newsletter media implementation evidence

Updated: 2026-09-18. All four pilots—the hub, Popty Cara, ASAP and The Brave—are released and operationally verified; Popty and ASAP also passed actual storage round trips. All 47 remaining demos are unreleased. The first candidate stopped on three public visual comparisons before deployment; the cause was host font drift, now reproduced and corrected in the quality process without baseline changes. See [SESSION_STATUS.md](./SESSION_STATUS.md) for the active handoff.

## Implemented and verified

- Shared Plate image controls, serializer, upload/library picker and attachments preserve the existing Puck string picker contract. Images support alt/decorative state, caption/link, width/alignment, replacement/removal and undo/redo. Changed code modules stay below 600 lines.
- Saved `bodySource` explicitly selects visual, HTML or text content. Switching views preserves the visual document; resuming it or replacing it from text requires confirmation. Arbitrary HTML-to-Plate conversion is outside scope.
- The public walkthrough shares the controls and serializer, with session-only files, PNG/PDF fixtures and simulated sending. Newsletter browser tests cover this simulation; installed-site storage verification is a separate pilot step.
- Trusted upload receipts and reviewed migration provenance establish site ownership. Unknown public file keys cannot fall through to the shared bucket or create Asset records. Durable image renditions survive source deletion and use the existing `{{appUrl}}` token.
- Attachment preparation verifies actual ownership, bytes, MIME/signature and encoded message size. Private snapshots use AES-256-GCM with a dedicated per-site key. Durable pending records precede storage writes; interrupted writes resume, and only ready records can load. R2 reads have a 60-second response/body deadline.
- Queuing freezes content and media before publication. Bytes and footer icons are prepared once per batch. Atomic delivery claims prevent concurrent submissions; ambiguous provider outcomes require review without automatic retries. Interrupted queue preparation requires operator recovery.
- Private snapshots remain pinned while referenced, then become eligible for bounded cleanup at least 30 days after release. Sent image renditions remain durable. Cleanup has a dry-run command and a daily scheduler vehicle.
- Social links use per-site HTTPS settings and omit unset entries. Provisioning preserves ASAP's five configured social accounts. Installed-demo real newsletter sending is rejected by the new server code unless explicitly opted in; provisioning alone does not enforce that policy in older live slots.
- Selected newsletter image assets and attachments are frozen. Third-party custom HTML/news-highlight image URLs and standard branding retain their previous behavior; arbitrary remote images are not fetched or frozen.

## Operational requirements

- Before any cron POST, prove the deployed endpoint is the new read-only-capable implementation. Old endpoints can ignore a `dryRun` request. `bun scripts/newsletter-dispatch-cron.ts --env-file=<production-env>` then performs the authenticated read-only check.
- Install schedulers serially with `bun scripts/newsletter-scheduler.ts --site-root=<controller> --install`. The default installs read-only checks and daily cleanup. `--enable-dispatch` additionally requires a verified empty queue and explicit demo opt-in where applicable. Backups are private; execution uses the stable HTTPS origin, timeouts and `flock`.
- Each site's release record must separately show live commit/health, nginx media routing, dispatch mode and daily cleanup installation. The fleet release runner does not perform the latter operations. Demos require cleanup even while real sending is disabled.
- `bun scripts/newsletter-media-cleanup.ts --env-file=<production-env>` is read-only unless `--apply` is supplied. Keep the media key while retained snapshots need it. Sent image storage must survive code rollback.
- Old slots lack frozen-manifest handling and the immutable-media endpoint. After feature usage, do not perform a generic old-slot rollback: first block newsletter admin mutation/dispatch endpoints and disable scheduled dispatch; inspect queued, sending and uncertain campaigns. Preserve the new image route/service and durable storage, or deploy a corrected media-capable commit. Record the concrete dispatch block before attempting rollback. Captured previous slots are recovery evidence, not authorization for blind rollback.
- Legacy migration uses reviewed manifests and checksum/CAS checks; a database record alone is insufficient ownership proof. The eight exclusions must not be automatically trusted.
- Fleet release uses the reviewed runner and each site's complete quality manifest, then the exact validated commit in an inactive slot. See [release instructions](../../ops/scripts/NEWSLETTER_RELEASE.md). Browser checks use local Playwright; Figma and Snapshot MCP are prohibited for this task. No real emails are a verification mechanism.
